藥草與洞窟

這個小遊戲不是手寫的。一份 GameSpec 交給 generate_game， 它產出三張地圖、三條任務鏈與一場終局戰鬥，接著讓驗證器、戰鬥模擬器和事件層腳本各自檢查一遍。 下面可以直接走走看——頁面跑的是這個 repo 自己的事件直譯器，用 esbuild 打包成瀏覽器版本。

這個遊戲是怎麼來的

每一格都是 spec 的函數，沒有人手動擺過一個事件。下面五個階段全在記憶體中的 ProjectSession 上跑完才決定要不要寫入磁碟——驗證沒過就什麼都不會落地。

戰鬥模擬

MZ 的傷害公式是一段 eval 字串，所以不需要瀏覽器也能算。這幾場是在 Node 裡各跑 300 次的結果； 你在上面觸發戰鬥時，勝負就是拿這裡的勝率擲骰決定的。

通關腳本

walkthrough 從頭玩到尾，斷言終局開關真的被打開；gates 反過來確認開局時每一道鎖都還鎖著。 兩份腳本是從 spec 推導出來的，不是從產生出來的事件反推——否則它們只會跟自己一致。 下面這顆按鈕就在你的瀏覽器裡跑同一份 runScenario。

這個頁面證明了什麼、沒證明什麼

把界線寫清楚，比讓 demo 看起來更厲害重要。

會動的是事件層，不是 MZ

MZ 的執行檔（js/rmmz_*.js、PIXI、場景圖）隨付費編輯器出貨，不在這個 repo 裡。 所以這裡沒有 MZ 的畫面，跑的是 packages/playtest 的直譯器：分支、迴圈、開關、 自我開關、物品、傳送、頁面條件都照 Game_Interpreter 的語意走。

畫面是通行旗標，不是美術

地圖上的方格直接畫 Tilesets.json 的通行旗標，由 mapgen 的 checkPassage 在 Node 端算好——那是 Game_Map.checkPassage 的移植。專案裡沒有任何圖檔， 所以事件在真正的 MZ 裡也還是隱形的，這裡用標記代替。

戰鬥沒有真的打

事件層只被「告知」勝負，傷害計算是 simulate_battle 的工作。 頁面拿模擬勝率擲骰，所以你會看到終局偶爾落敗——1% 的那一邊。

沒有經過真正的編輯器

產出的 data/*.json 從未被 RPG Maker MZ 開過。格式假設集中在 io/format.ts 一個模組裡，就是為了哪天對上真實編輯器輸出時只需要改一個檔案。

重現這一頁

在 repo 根目錄執行，產出的 HTML 就是你正在看的這一份。

npm install && npm run build
node demo/generate-demo.mjs /tmp/game.json     # spec → 專案 + 報告
npx esbuild demo/browser-entry.js --bundle --format=iife \
  --platform=browser --minify \
  --alias:@rmmz-kit/core=./demo/core-shim.js --outfile=/tmp/runtime.js
node demo/build-page.mjs /tmp/game.json /tmp/runtime.js demo.html
由 packages/gamegen 產生、packages/validate 檢查、packages/battlesim 模擬、packages/playtest 執行。專案沒有被 commit——所有寫入都留在 ProjectSession 的交易裡。
